# Customer qualification

Qualification is a project-scope assessment, separate from customer lifecycle status and any advertising integration. A customer can be qualified, not qualified, unclear, or not assessed. Budget, location and timing are not rejection criteria. The default rules cover custom furniture and cabinetry; ambiguous descriptions remain unclear. The initial 0.8 confidence threshold is provisional, not a measured accuracy guarantee.

New linked website inquiries are assessed asynchronously through the existing Workers AI binding using `typesafe/jev`. The website submission remains accepted if assessment fails, and no automatic retry infrastructure is added. Staff can assess/reassess existing customers from their detail view. Input priority is the latest website project description, then latest opportunity description, then the latest staff-authored note, then customer notes. Empty input or an unavailable/invalid model response never becomes a negative classification. No automatic historical backfill is performed.

Every assessment stores its original classification, confidence/probabilities, reported model version, rules version and text, description snapshot, source reference and timestamp. Only the description is sent to the model; names, contact identifiers, budgets and ad attribution fields are not explicitly sent. Customer descriptions may themselves contain personal information. Treat descriptions as data, not model instructions. The returned response must satisfy the decision schema. A delayed result for a superseded description is discarded.

Staff mark an assessment correct or incorrect. Incorrect reviews record the expected classification; all reviews include the reviewer and review time. Reviews are appended against the original assessment, preserving repeated assessments and evaluations. They do not alter the original classification, retrain the model, affect subsequent prompts, or trigger delivery to any external system. Assessments and reviews remain available through the customer detail response and authenticated `GET /customers/:id/qualification` endpoint, with existing workspace authorization.

Migration 0039 must run before deploying the API. Deploy API before the customer UI. Customer deletion follows existing cascade semantics. The history is protected from update/delete through application routes, and remains available for future evaluation or a destination-neutral qualification signal. No Meta connection, webhook, queue, export, or budget change is included.
